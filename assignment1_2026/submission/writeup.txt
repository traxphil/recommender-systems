### Core Ideas of my Approach - - - - - - - - - - - - - - - - - - - - - - - -

Early on, I realized that I struggled with overfitting my models and Surprise has no real way of doing early stopping. This is why I
wanted to use Pytorch, with the motivation to have more overall control and insignt into what is happening. This would also allow me to 
apply adaptive learning rates and have more control overall when it comes to fine-tuning my code. But this came with significantly more
work than I initially expected. The main difficulty came with setting up the whole infrastructure, handlers, and architecture of my
solution approach, because I quickly realized that I would lose any sense of overview, if I just wrote everything into a single file.

This is why this whole project repository has grown to the size that it currently has. I have followed a strict approach of modularization
for my individual responsibilities in my code (I'm also taking CSE 210 at the moment and this class also really teaches the importance of
modularization and separation of concerns. I have applied these ideas in this project extensively).

I also want to put a large emphasis on mathematical understanding of the models and ideas I apply in this project. Using pytorch also makes
it significantly more important to have a closer look at the actual math behind the models. This level of insight would have been almost 
entirely obstructed if I stuck with the SciKit Surprise models, even though it might have been significantly easier. In all of the notebooks
I have included the mathematical descriptions of the models. This whole project quickly grew larger than I initially expected and I want to
be able to use the code I developed here in the future as well. I hope this repository will be able to serve me as a reference for future
use of pytorch and other machine learning projects. Therefore, this project is more or less also an investment into my future knowledge base
going beyond just the scope of the class. 

This writeup will also reference the sources of where I found my ideas and how I have included them into the implementations for the 
individual tasks. For all of the implementations, I opted to use ensemble models as this generally seems to be a good approach for building
competitive recommender systems that generalize well. I would have probably preferred to keep the implementation a bit simpler and smaller
but the pressure of the leaderboard made it almost necessary, to pursue more advanced solutions. 

I have also discussed my ideas with Claude to come up with better ideas, improve existing approaches, or identify shortcomings in my ideas. 
But this primarily served the purpose of guiding me through the material and helping me out when I was stuck. I have no intention of just
letting an LLM write my code as I personally also see absolutely no benefit in doing that. But I have to admit dhat it definitely was an amazing 
help, especially when I went for the more complex models or repetitive notation tasks (e.g. for the formulas).

### Loading and Processing of data - - - - - - - - - - - - - - - - - - - - - - - -

The loading code is in lib/data_loading.py and is the same for Task 1 and Task 3 (load_rating_prediction_task):

-   Both CSV files are read as plain string columns. Every user and book id gets a row number in the order it first appears in
    the training file. Row 0 is reserved for ids that only appear in the test file (Task 1 has none). These row numbers are the
    indices into every embedding table and sparse matrix.

-   The ratings are kept as aligned arrays in a RatingData object: user_rows[k], item_rows[k] and ratings[k] describe rating k
    (Task 3 also has days[k] / timestamps[k]). A RatingTask bundles the training split, the validation split, both together,
    the test pairs and the number of user / book rows.

-   10 % of the training file is held out at random as the validation split (VALIDATION_FRACTION, fixed SPLIT_SEED). No model
    fitted on the training split ever sees these ratings, also not through its biases or its book similarities. N(u) may contain
    the validation and test pairs as "read", but never their ratings. This keeps the validation MSE honest, so it can be used for
    early stopping, for the sweeps and as the training data of the blend.

-   Time is only loaded if the test file has a timestamp column. The Task 1 test file has none, so days and timestamps are None
    in Task 1 and no model can use time by accident.

-   When a model needs all ratings of a user or of a book at once (SVD++'s N(u), the kNN residuals, AutoRec, the Bayesian FM
    features), it builds a scipy sparse matrix with one shared helper (sparse_matrix_from_entries: built as COO, used as CSR).

-   The other tasks have their own loaders in the same file: load_pair_choice_task (Tasks 2, 4: a random 10 % of the
    interactions as positives, each with negatives drawn from other interactions, as in the test), load_next_item_task (Task 5:
    each user's last interaction held out) and load_time_gap_task (Task 6: each user's last gap held out).

Why I didn't use one super large matrix:
The full user x book matrix would have 30,909 x 51,007 = 1.58 billion cells (6.3 GB as float32), but only 1.86 million of them
(0.12 %) are filled. Apart from the memory, a dense matrix would also mix up "not rated" with "rated 0 stars" (on
Goodreads mostly "shelved without stars"). So the ratings stay a list of (user, book, rating) entries, the models train on mini-batches of these entries, and
sparse matrices are only built where a model really needs whole rows.


### Central Logic of assignment1.py - - - - - - - - - - - - - - - - - - - - - - - -

assignment1.py connects the data, the settings and the models; it contains no model code itself. For every task it has:

-   the file paths and a load_taskN() function,

-   one small train_taskN_<model>() function per sub-model, which only calls the model's training function with its settings
    from lib/config.py. All hyperparameters live in config.py, so this file reproduces the submitted predictions,

-   a registry TASKN_SUB_MODEL_TRAINERS (model name -> training function) and train_taskN_models(), which trains every model the
    submitted blend uses,

-   train_taskN_blender(), write_taskN_predictions() and run_taskN(), which runs the whole task from loading to the prediction file.

Every training function returns the same ModelResult: the model, its training history, its validation predictions and its test
predictions. The predictions are all the blender needs, which is why the notebooks store every sub-model in
trained_models/<task>/<model>.pt and can redo the blend after a kernel restart without retraining anything.


### Training Pipeline - - - - - - - - - - - - - - - - - - - - - - - -

Every sub-model goes through the same four steps:

    1. fit on the 90 % training split
    2. predict the validation ratings -> these predictions are the training data of the blender
    3. refit from scratch on 100 % of the training file (training + validation split)
    4. predict the test pairs -> the blender combines these

The refit gives the final models 11 % more ratings. The blender learned in step 2 is then applied to the predictions of step 4,
the same "probe -> quiz" scheme the Netflix Prize teams used for their blends [2].

For the PyTorch models these steps are one shared function (fit_refit_and_predict in lib/torch_trainer.py):

-   Mini-batches of single ratings in random order, Adam, loss = MSE + L2 penalty. Each user's / book's penalty is divided by its
    number of ratings, so over one epoch every parameter is penalised about once, as in the usual sum-of-squares objective [1].

-   The biases start at the closed-form bias model and the factors at small random values, so epoch 0 already equals the bias
    baseline and training can only improve on it.

-   After every epoch the validation MSE is measured. The best weights are kept, and training stops after early_stopping_patience
    epochs without improvement. Early stopping was the main reason I moved from Surprise to PyTorch.

-   The refit trains a fresh model for exactly the best number of epochs, since there is no validation data left to stop on.

The models without gradient descent (bias model, item kNN, zero model, Bayesian FM) and AutoRec (own training loop) follow the
same four steps with their own code. The sweeps in /sweep call exactly these training functions, with the refit switched off.


### Sweeping for Hyperparameter Identification

-   sweep/grid_search.py: tries every combination of the given settings for one sub-model (fit on the training split, scored on
    the validation split, no refit) and writes one JSON file per sweep (sweep/output/<task>/<model>_<time>.json).

-   sweep/ensemble_search.py: tests which stored sub-models a blend should combine, out-of-fold on the validation rows over several
    fold splits; a change within ~2 standard errors counts as noise.

-   The chosen settings and the scores that decided them are noted next to each setting in lib/config.py.



# #########################################################################################
# Task 1 - rating prediction (no timestamps)
# #########################################################################################

Predict the stars of 20,000 (user, book) pairs, scored by the MSE. Ratings of 0 stars ("shelved without stars" on Goodreads) are
not part of the leaderboard (lecture of 6 Nov; my public score matched the validation MSE without zeros) -> every rating model
trains on the ratings 1 - 5 only, and the blend is fit and scored on validation ratings > 0, predicting 1 - 5.

Sub-models (settings in lib/config.py, formulas in task1_ensemble.ipynb):

* Bias model: global mean + user offset + book offset, fitted in closed form. Works because most of the variance in ratings is
  "this user rates high" / "this book is liked" [1]. Manual features: none (user and book ids).
* SVD: biases + dot product of learned user and book factors. Works because tastes and book properties live in a low-dimensional
  space, so similar users / books share factors [1], [16]. Manual features: none.
* SVD++: SVD where the user factor also contains the factors of all books the user rated. Works because *which* books someone
  rates says something about them, which helps users with few ratings [4]. Manual features: the user's set of known books N(u)
  (rated, shelved with 0 stars, and the validation / test pairs; their ratings are never used).
* Item kNN: baseline + similarity-weighted average of the user's residuals on the 100 most similar books. Works because it keeps
  local "people who liked X more than expected also liked Y" effects that low-rank models smooth out [6], [7]. Manual features:
  shrunk cosine similarities of the books' residual columns.
* Zero model: logistic regression for P(rating = 0). Kept as a blend input (it still sees the zeros) because users who shelve
  without stars rate differently. Manual features: user's and book's share of zeros (shrunk), their numbers of ratings.
* Factorization machine: all pairwise interactions between user, book and two context fields. Works because it lets e.g. a
  user's taste for popular vs. niche books be learned [9]. Manual features: user activity bucket, book popularity bucket.
* Bayesian factorization machine: the factorization machine averaged over Gibbs samples (myFM) instead of one optimum. Works
  because the averaging regularises automatically and hardly overfits, the strongest single model here [10], [11], [19].
  Manual features: user, book, N(u) as in SVD++, N(i) (readers of the book).
* Rating transformer: the asked book attends over the user's rated books (book embedding + stars). Works as a learned, non-linear
  mix of kNN (attention = book similarity) and SVD++ (history describes the user) [20], [21]. Manual features: the user's
  history of (book, stars), the asked book hidden from it.
* I-AutoRec: an autoencoder compresses each book's vector of rating residuals and reconstructs it. Works because its non-linear
  errors differ from the factor models' [12]. Manual features: the book's ratings (bias residuals, 25 % masked in training).
* Integrated model: SVD++ plus a learned neighbourhood (weights between a book and its 100 neighbours). Works because global
  factors and local book-to-book effects are fitted together [4]. Manual features: N(u) as in SVD++, the item kNN's neighbourhoods.

Blend: ridge regression on the ten validation predictions (the sub-models were fit without these ratings), 5-fold out-of-fold
scored; applied to the test predictions of the sub-models refit on all data and clipped to 1 - 5. The bias model and the item kNN
share one baseline, so the blend effectively uses the kNN's neighbourhood correction. A LightGBM blender was slightly worse (0.5378).

Result (validation MSE on ratings > 0): best single model (Bayesian FM, rank 192, 2 sampling chains averaged) 0.5380 -> blend
0.5339 (one chain: 0.5408 -> 0.5360, leaderboard 0.5341; with zeros in training: 0.5789 -> 0.5495, leaderboard 0.5455).


# #########################################################################################
# Task 2 - which of two books did the user read? (no timestamps)
# #########################################################################################

Each test row has a user and two books; one was read, the other is the book of a random other interaction. Because the negative
is drawn in proportion to popularity (lecture of 10 Nov), popularity alone carries no signal, so my validation pairs are built the
same way. Every sub-model scores (user, book); a pair blender decides which book is the real one.

* Popularity: log(1 + #readers of the book). Barely separates a pair on its own, but tells the blender how to read the other
  scores for popular vs. rare books. Manual features: book reader count.
* Item cosine: sum of the cosine similarities between the book and the books the user read. Works because people read books
  that are read by the same people ("readers of X also read Y") [1] Ch. 4. Manual features: the 0/1 "who read it" columns,
  top 1,600 neighbours per book.
* EASE: a linear autoencoder whose book-to-book weight matrix has a closed form (no training loop). Works because it learns
  which books predict which, including negative weights, and is a very strong top-N baseline [13]. Manual features: none.
* Mult-VAE: a variational autoencoder reconstructs the user's whole reading history through a small latent code. Works because
  it is non-linear and trained to fill in held-out books [14]. Manual features: none.

Blend: LightGBM on both books' scores, their difference, "already read by the user" and the user's number of interactions; every
pair is used in both orders, 5-fold out-of-fold scored. The test file has no timestamps, but the training file does, so the
blender also gets:
* User span features: the book's first / 10 % / median read date (by anyone) vs. the user's first / median / last date and the
  share of the book's reads inside the user's active span. Works because the negative often comes from a time the user was not
  reading at all.
* Reading window: how often other readers read the book within 5 books (in time order) of a book the user read, raw and per
  sqrt(readers). A time-local "readers of X also read Y", sharper than plain co-occurrence.
The validation draws 4 negatives per held-out book (as Task 5). Result (validation accuracy): 0.9369 (leaderboard 0.9406) ->
span + window 0.9401 -> bigger LightGBM 0.9403 -> 4 negatives 0.9409.


# #########################################################################################
# Task 3 - rating prediction with timestamps
# #########################################################################################

Same as Task 1, but the test rows have a timestamp that lies inside the training period (interpolation, not forecasting). The Task 1
models are trained again on this data (timestamps ignored, zeros left out of training; the two factorization machines only in their
time-aware form), plus temporal models:

* Time-aware bias model: biases + a 30-bin global time trend, a time-varying book bias, a user drift over their rating lifetime and
  per-user biases for the day / week / month / quarter / year / 1000 days of the rating. Works because users rate differently in
  different phases and on "binge" days, and the test rows sit between known ratings [5]. Manual features: time bin, the user's
  periods, dev_u(t) = signed |t - mean day of the user|^0.4.
* timeSVD++: SVD++ on top of the time-aware biases [5]. Works because it combines tastes with the temporal offsets. Manual
  features: N(u) + the temporal bias features above.
* Time-decayed item kNN: the item kNN, but the user's neighbouring ratings count more the closer in time they are to t [5], [8].
  Works because a user's taste and mood are most similar around the same time. Manual features: decay exp(-|t - t_uj| / 3000 d)
  with a floor of 0.7.
* Temporal zero model: the zero model + the user's zero share in windows of 0 / 7 / 30 / 365 / 1000 days around t. Works because
  zeros come in shelving sessions (45 % of ratings are 0 if the user gave another 0 that day). Manual features: these windows.
* Time-aware factorization machine: the Task 1 factorization machine + one-hot calendar fields, so e.g. a book's seasonal
  popularity or a user's habits over the years are learned [9]. Manual features: activity / popularity bucket, month, year.
* Time-aware Bayesian factorization machine: the Bayesian FM + one-hot weekday, month and year + one-hot (user, 365-day period)
  and (user, 1000-day period) of the rating; the strongest single model of Task 3 [10]. Works because a user's rating level
  drifts over the years [5], and the period gets its own factor too. Manual features: user, book, N(u) (every known pair, as in
  Task 1), N(i), weekday, month, year, the user's 365 / 1000-day period.

Blend: ridge regression over all 14 sub-models, fit on the validation ratings > 0 (a LightGBM blender with time features was
worse). Result (validation MSE on ratings > 0): best single model (2 sampling chains averaged) 0.6746 -> blend 0.6671 (one
chain: 0.6765 -> 0.6677, leaderboard 0.6778; with zeros in training: 0.7105 -> 0.6776, leaderboard 0.6883).


# #########################################################################################
# Task 4 - which of two books did the user read, at a given time?
# #########################################################################################

Task 2 with a timestamp per pair. The negative is still drawn without regard to time, so "was this book being read around t?" is a
strong signal on top of the Task 2 models (popularity, item cosine, EASE, Mult-VAE, trained on this data):

* Time-weighted EASE: the EASE weights, but the user's books read close to t count more (exp(-|t - t_uj| / 180 days)). Works
  because what someone reads at a time is closest to what they read around then. Manual features: the time decay.

Blend: the Task 2 pair blender + time features per book: interactions within +-30 days of t, the book's age at t, and how the
other readers' reading is placed around t (readers within 7 / 30 / 90 / 365 days after t, within 30 days before, share after t,
days to the first reader after t and since the last one before). The real book is typically being read around t, the negative
is from a random time. Plus the Task 2 user span and reading window features and 4 negatives per held-out book. Result
(validation accuracy): 0.9325 (leaderboard 0.9372) -> span + window 0.9329 -> 4 negatives 0.9341.


# #########################################################################################
# Task 5 - which book comes next in the user's sequence?
# #########################################################################################

The positive is the book right after the user's last training interaction; the test has no timestamps, so "now" = the day of
the user's last interaction. Validation: each user's last interaction is held out (leave-last-out) with negatives drawn as in the
test. Sub-models: popularity, item cosine, EASE, time-weighted EASE (recency relative to "now"), Mult-VAE (as in Tasks 2 / 4) and:

* Transition model: a first-order Markov chain "book i follows book j within the next 100 books" (decayed by distance), voted by
  the user's last 20 books. Works because series and "read next" orders are shared across readers [1] Sec. 7.4. Manual
  features: reading order, step and context decay.
* SASRec (three runs: the last 50, 100 and 200 books): a causal transformer over the user's reading sequence that
  predicts the next book, trained with negatives drawn like the test negatives (in proportion to popularity). Works because
  attention picks out the books in the history that matter for what comes next [15]. Manual features: none (book ids in order).

Blend: the pair blender with the Task 4 time features relative to "now", a bigger LightGBM (63 leaves, 800 trees) and sequence
features of the candidate: how often other readers read it right after / within 5 books after the user's last book, its share
of the last book's followers, "within 5 after" the 2nd / 3rd-last book and "within 5 before" the last book. Works because
reading orders (series, lists) are shared across readers. The validation draws 4 negatives per held-out book, so the blender
learns from 4x the pairs (scored on the 1-negative pairs, as the test). Result (validation accuracy): 0.9246 (leaderboard
0.9192) -> sequence features 0.9250 -> 4 negatives 0.9269 -> + the 200-book SASRec 0.9275 (leaderboard 0.9225) -> + the
Task 2 user span and reading window features 0.9280.


# #########################################################################################
# Task 6 - time until the user's next interaction
# #########################################################################################

Predict the seconds until the user's next interaction (the next book is given), scored by the mean absolute error -> the
conditional median is the best prediction, so the models fit an L1 loss on log(1 + gap). Validation: each user's last gap.
Some timestamps are corrupt (years 2557 - 2560, likely Buddhist-era dates, and 3103); they create a few gaps of hundreds of years
in the test that no model can predict.

* Median baseline: the median of the user's earlier gaps (the assignment's baseline).
* Linear median autoregression: the next gap from the last gaps and the user's gap statistics with an absolute loss [1] Sec. 7.1.
  Manual features: last 3 gaps, median / mean of the gaps, number of interactions.
* LightGBM (submitted): gradient-boosted trees with an L1 loss. Works because the gap depends non-linearly on the user's rhythm,
  the calendar and above all on when the next book is being read by others. Manual features: last 3 gaps; median / mean / std /
  min / max of the gaps; share of gaps under a day; number of interactions and active span; year, hour and weekday of the last
  interaction; the next book's popularity, first and median reading day relative to the user's last day and share read after
  it; when other readers read the next book relative to the user's last interaction (first, 10 / 25 / 50 % of the later
  readers, the last earlier reader, share within a week / month / year); book-to-book timing (readers of both the user's last
  book and the next book: how many, how often the next one came second, median time between them). The user's 4 previous gaps
  are added as extra training rows (features computed as of that point), with their position from the end as an input;
  255 leaves, 1000 trees. Bagging (averaging models on random row / feature subsets) and more earlier gaps (6, 8) did not help.

Result (validation MAE): median baseline 139.5 days, LightGBM before the new features 83.6 -> 81.1 days (leaderboard 8.73M s)
-> 80.4 days with the extra rows (leaderboard 8.58M s) -> 1000 trees 80.38 days.
